# Design of the ontology ingestion framework

## Scope and references

The core package, `ontology_ingest`, implements contract version 1 for small and medium ingestion jobs whose entities and edges fit in memory. It does not contain a producer, a domain-specific entity name, a workspace credential, or a hard-coded dataset catalogue; the GeoBasin producers and the Foundry module sit beside it in `producers/` and `foundry_agent/`. Producers depend only on `ontology_ingest.contract.DatasetWriter`. The preparation logic works through file-storage and table-writing interfaces. The same preparation function runs on a local Python interpreter or inside a generated notebook.

Regression testing is offline. The Microsoft product references include the [ontology definition article](https://learn.microsoft.com/rest/api/fabric/ontology/items/ontology-definition), the [Fabric IQ connection article](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/fabric-iq) and the decoded working WindFarm sample definition. The last section describes the platform behaviours the implementation depends on and its known limitations.

The implementation relies on behaviour confirmed in Fabric for the pure-Python notebook metadata, the notebook and storage token audiences, schema-enabled Delta paths, metadata refresh, table-backed entity relationships, the inactive target-side relationship for self-links, synonym syntax, multiline descriptions, and the ontology MCP handshake and tools. In particular, notebook exit values must be fetched from the notebook-specific execute-instance endpoint, not from the generic item job polling endpoint. The implementation uses that route.

## The six steps and component boundaries

In the first step, an upstream producer writes one dataset directory. `DatasetWriter` collects entities and edges, validates producer type names, merges duplicate producer entities using first-non-null values, removes duplicate edges, and writes deterministic CSV files and metadata. It deliberately does not invent a `producedAt` time; a producer can provide `produced_at` explicitly. The output directory is the dataset directory itself, rather than a parent under which the writer creates another named directory.

In the second step, `land` freezes file bytes and uploads a content-hashed snapshot with a bounded pool of eight workers. The framework archive is uploaded too, and the landing manifest is written only after every upload succeeds. A matching existing manifest skips the dataset uploads and uploads only the archive. `prepare.run` discovers dataset directories, retains raw input, expands properties, normalizes missing values, derives quantities, casts candidates, merges valid values, validates edges, and constructs explicit Arrow tables. A complete model preflight occurs before any table writes. By default, raw and binding tables go into separate run-scoped schemas, never the schemas used by the previous published snapshot.

The raw schema holds one audit table per source file and `quarantine_edges`. Every original raw field is represented as a string, while `_row_number` is an integer and `_ingested_at` is an aware UTC timestamp. The binding schema holds one typed table per nonempty entity type and one two-column junction per nonempty typed relationship. It never uses an entity table as a junction. This follows the documented distinction between entity backing tables and table-backed entity relationships in the [ontology definition contract](https://learn.microsoft.com/rest/api/fabric/ontology/items/ontology-definition#entityrelationshipstmdl-entityrelationship-file-ontology-extension).

The third step requires a completed preparation marker, verifies binding row counts before changing the ontology, obtains the lakehouse SQL endpoint, and refreshes metadata for every required schema.table. It then generates TMDL, publishes the definition, reads it back and verifies the returned structure and row counts. Only after these checks succeed can retention delete older published schemas. `publish_plan` is shared by the local command and the generated notebook. `tmdl` validates names, keys, property types, references, synonyms and the model budget before rendering. Structural comparison tolerates service reordering and default-value elision, as described in the [definition documentation](https://learn.microsoft.com/rest/api/fabric/ontology/items/ontology-definition#folder-layout-and-naming).

In the fourth step, `verify` compares every entity and junction row count with the plan and verifies the returned ontology structure. It can optionally initialize the ontology MCP endpoint, list tools, and call one configured tool. The MCP client returns the complete tool result, including text, structured content and metadata. It treats JSON-RPC errors and `isError` tool responses as failures rather than successful smoke tests. Ontology calls are synchronous, consistent with the [Fabric IQ endpoint behavior](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/fabric-iq#find-your-fabric-iq-server-details). The live endpoint once answered HTTP 200 with an empty body after an 87-second query, so `call_tool` retries once when a response carries no message for its request and then raises `MCPIncompleteResponse`.

The fifth step builds the graph as a separate graph model rather than through the ontology. Fabric's **Manage graph** reports every entity type that this framework publishes as an unsupported data source, because the public definition API keeps only one of the eight `ONT_` connection annotations that the portal writes on each bound partition ([FABRIC_KNOWLEDGE.md](../../docs/FABRIC_KNOWLEDGE.md)). `graphmodel.py` therefore renders a [Graph Model definition](https://learn.microsoft.com/rest/api/fabric/articles/item-management/definitions/graph-model-definition) from the published plan. It has one `DeltaTable` data source per binding table, all named under a single `itemReferences` entry for the lakehouse with paths relative to it, because version 1.1.0 of the data source schema refuses a source without `referenceName`. Each entity type becomes a node type labelled with its name, keyed on its key property and carrying every property with its GQL type. Each relationship type becomes an edge type labelled with its relation and connecting its two node types, so several relationship types can share one label, such as `locatedIn`. Names that are not plain identifiers are reduced to letters, digits and underscores, and a collision after that cleaning is refused. `graph-model` reads the run's `published-plan.json`, refuses to continue when retention has already removed the run's binding schema, creates or updates the item, and then runs the [RefreshGraph job](https://learn.microsoft.com/rest/api/fabric/graphmodel/background-jobs/run-on-demand-refresh-graph) and waits for it. Creating a graph model starts a refresh by itself, so a request that Fabric reports as `Deduped` waits instead for the most recently started job that was not skipped. The step then compares the loaded node and edge types from [Get Queryable Graph Type (beta)](https://learn.microsoft.com/rest/api/fabric/graphmodel/items/get-queryable-graph-type(beta)) with the plan, and runs one GQL count per node type and per edge type, constrained by both endpoint labels, against the plan's row and edge counts. A graph model created through the REST API cannot load data until it has been opened once in the portal ([Manage data in graph](https://learn.microsoft.com/fabric/graph/manage-data)), so a failed refresh is reported with that instruction.

`graph.py` and the `graph` command read the graph model named by `graph_model_name` when one is configured. Otherwise they read the graph model that Fabric creates beside the ontology, found by its name, which Fabric forms from the ontology name and the ontology id without dashes, so the graph of another ontology is never used. Without a query, the command calls Get Queryable Graph Type, which the live service answers with HTTP 204 and no body until a graph has been loaded, and reports either that the graph cannot be queried yet, together with the step that loads it, or its node labels with their keys and its edge labels with the node labels they connect. With a query, it runs GQL through `FabricClient.graph_execute_query` and turns the service's HTTP 400 `GraphNotQueryable` error into a message with the same step and exit status 3. The command writes no run state, and the code does not delete or otherwise manage the graph model, eventhouse and KQL database that Fabric creates beside each ontology.

The sixth step is automated by the separate `foundry_agent` module, which needs `azure-ai-projects` and `azure-identity` only when it runs. `connect` creates or updates a RemoteTool connection in the Foundry project through Azure Resource Manager. The connection points at the ontology's MCP endpoint with `authType` UserEntraToken and the Power BI audience, so every query runs with the caller's own Fabric permissions. `agent` creates an agent version with the Fabric IQ tool, and refuses to add a version to an existing agent that is not wired to this ontology's connection unless forced. `ask` runs in background mode and polls, because Foundry stops a synchronous MCP tool call after 100 seconds ([known limitations](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/model-context-protocol#known-limitations)), and it exits with status 1 when the answer did not complete. The account name becomes the host that receives the Azure AI token, so it must be a single DNS label; the subscription must be a GUID and every other name a single resource name, and path segments are percent-encoded as well. The ontology is found through the paginating `FabricClient.find_item`, and token-bearing requests never follow redirects. Before sharing an agent, the operator must still review permissions, publication state and data-boundary implications, following the [Fabric IQ connection guidance](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/fabric-iq#authentication-and-security).

## Contract reading and naming decisions

Discovery accepts a landing root containing multiple dataset directories, and also a single dataset directory as the root. A directory qualifies through `dataset.json`, `entities`, or `relationships`. Two files with the same type stem in one dataset are rejected instead of guessing whether CSV or JSONL should win. Two directories with the same logical dataset name are rejected because dataset-name priority ties and provenance would otherwise be ambiguous. A stale producer output file is not silently left active: `DatasetWriter.close` refuses obsolete CSV files and competing JSONL files, and asks the producer to use a clean destination or remove the stale file explicitly. It does not delete unrelated files.

CSV parsing accepts a UTF-8 BOM, quoted commas and newlines, and requires unique nonempty headers. Expansion treats empty or whitespace-only strings and the case-insensitive placeholders `not recorded`, `none`, `n/a`, `unknown` and `-` as null in CSV, JSONL and JSON properties. Raw audit tables retain the original input text; the change applies to binding candidates, not raw evidence. Zero and false remain values. The same missing-value rule governs duplicate merges in `DatasetWriter`. Wrong-width CSV rows and malformed JSONL lines are retained in raw data and reported. The binding reader keeps the first duplicate identifier within an input file. Identifiers are trimmed strings; empty or placeholder identifiers are invalid. Invalid typed labels become null and are reported.

A property’s canonical identity across datasets is its sanitized column name. Raw keys such as `Operator` and `operator` in different datasets map to the same column and merge by normal dataset priority. `column_names` is applied separately for each dataset and entity type, so suffixes disambiguate distinct colliding keys only inside that dataset. The quality report exposes `columnMaps[entityType][datasetName][rawKey] = column`. Raw keys are sorted before suffix allocation. A property cannot occupy `id`, `label` or `source_datasets`. When a non-null flat column and `properties_json` contain the same raw key, the flat value wins and a quality error records the collision. The original JSON remains in the raw audit table.

Raw source headers are sanitized too. This is deliberate: arbitrary CSV headers are not necessarily legal Delta columns, and the package must not enable column mapping to preserve them. Each file's `rawColumnMap` records the reversible original-header-to-column mapping. The values and the original source file remain available. Audit-column names cannot be overwritten by producer fields.

Entity and raw-table name collisions caused by normalization are fatal, rather than resolved with table suffixes that would violate the specified naming convention. Property collisions use the requested stable numeric suffixes. The naming functions perform Unicode decomposition before ASCII folding so superscript dimensions such as `km²` become `km2`. The only namespace emitted is the default namespace. Names with path separators, control characters or namespace markers are rejected for this version rather than being interpreted as filesystem paths or undeclared namespaces.

## Typing, derivation and merge decisions

A common column type is chosen from the declarations or all non-null source candidates, not a sample. Each candidate is cast to that type before priority selection. Booleans remain distinct from integers, int64 overflow becomes a string under inference, and mixed integer and floating-point families become doubles. Incompatible families remain strings unless a declaration requires a cast. Structured JSON values become deterministically ordered JSON strings. All-null columns have an explicit string type unless metadata declares another type.

Calendar ISO dates and timestamps are parsed with the standard library, naive values are assumed to be UTC, and aware values are converted to UTC. The Arrow representation is `timestamp[us, tz=UTC]`. Additional timestamp fractional precision is normalized to microseconds because that is the required storage representation. Integer and double types use Arrow int64 and float64. The implementation uses only APIs available in Arrow 17 and does not depend on pandas.

Declared `dataType` metadata wins over inference. Entity-specific dataset priority and then dataset name select conflicting declarations; alternatives are reported. Metadata matches the canonical column first and that dataset’s raw key second. The three framework properties stay strings. A failed cast becomes null before the merge, increments `castErrors`, and permits a valid lower-priority candidate to win. Within a dataset, a valid native value precedes derived candidates, but an invalid native value cannot block a valid derived candidate. Explicit numeric, boolean or date declarations are authoritative: inconsistent display strings are cast failures, not invitations to create shadow properties such as `total_depth_m_m`. Unobserved metadata-only properties are not invented.

A declared `decimal` is normalized to ontology `double` and an Arrow float64 column. The previous fixed decimal128(19,4) caster has been removed, so extra fractional digits are no longer discarded merely for exceeding scale four. Legacy decimal plan annotations also render as double. This follows the lakehouse-to-ontology type mapping verified in Fabric, rather than relying on unverified ontology decimal binding. Float64 is approximate and is not a fixed-precision financial representation; producers requiring exact decimal text should declare a string or carry an additional exact textual value.

Quantity derivation happens per dataset and entity type on display-string columns before typed merging. Every meaningful value must have a consistent direct or parenthesized number/range shape and unit. Hyphens, en dashes, em dashes and U+2212 are range separators; U+2212 also works as a numeric minus sign. Endpoints are ordered into numeric minima and maxima. Bare numbers and bare ranges do not acquire a unit. Identifier-marked columns are excluded, while measurement names such as `reference_depth` remain eligible. Units containing leftover digits are rejected, with a narrow exception for recognized dimensional units `m²`, `km²`, `m³`, `km³` and their normalized spellings. A literal ban on every digit would incorrectly disable the required square-kilometre area derivation. No conversion between different units is performed.

A derived name is a canonical column name too, so a derived `total_depth_m` shares the native `total_depth_m` column. Native and derived candidates remain separate until they have been cast to the common column type. Dataset priority is applied first, with native candidates before derived candidates within that dataset. The highest-priority valid non-null candidate wins, and remaining valid candidates are compared against that published value. Integer and floating-point candidates use their common numeric type instead of comparing their original textual representations.

The plan retains `derivedFrom` only when every valid non-null contribution is derived and the source column is unambiguous. Null or uncastable native values do not make a column mixed. Mixed native and derived columns retain their unit and use a native-property description. Per-dataset derivations remain visible in `derivedColumns`, including candidates that lose priority selection.

Property descriptions prefer declared metadata. Otherwise they name only the most human-readable raw key, preferring a key containing a space or capital letter over the unchanged sanitized column name. They do not concatenate aliases such as “Depositional environment and depositional_environment.” Source titles fall back to dataset names and are limited to three distinct titles followed by the number of additional sources. Pure-derived descriptions spell out known units, name the original display key and include a usable example. All prepared property descriptions are single-line strings of at most 3,999 characters.

The cross-dataset merge is column-wise and counts conflicts on canonical typed values. The string `1965` and integer 1965 agree after an int64 cast; 4440.0 and 4440 agree as a double; equivalent UTC timestamps agree after normalization. The real disagreement between 3851.8 and 3852 still counts. Failed casts are reported separately and are not conflicts. Synonyms are unioned and sorted, and `source_datasets` identifies every contributing dataset. Display values and numerical derivations can still originate from different datasets, so per-property winner provenance remains a useful future enhancement.

Binding strings over 65,535 UTF-8 bytes are rejected before writes rather than truncated. Truncating an identifier could corrupt relationships, and truncating evidence text could change its meaning. This is a deliberately strict data-quality policy. Descriptions, by contrast, are trimmed to the requested 4,000 characters, and each emitted line is a separate `///` comment. Property and collection limits follow the saved [ontology payload limits](https://learn.microsoft.com/rest/api/fabric/ontology/items/ontology-definition#payload-limits).

Relationship identity consists of relation name, source type, source identifier, target type and target identifier. Deduplication follows identifier trimming. Only edges that survive quarantine determine polymorphism and relationship names. An invalid pair cannot rename a surviving monomorphic relationship. Empty files and relations with no valid edges are skipped and reported. A known empty entity type produces a missing-endpoint reason, not an unknown-type reason. Quarantine precedence remains empty identifier, unknown source type, unknown target type, missing source and missing target, and each distinct invalid edge retains its first source-file provenance.

## Identity, transactions and persistence

UUID5 lineage tags are derived from fixed semantic identities for tables, columns, entities, properties, expressions and ontology entity relationships. Native TOM `relationship` blocks intentionally omit `lineageTag`, following the supported property list in the [definition contract](https://learn.microsoft.com/rest/api/fabric/ontology/items/ontology-definition#relationshipstmdl-relationship-file) and a definition the service accepted. Their names remain deterministic. Unchanged names and references produce unchanged supported tags regardless of input ordering, run identifiers or timestamps. Table and column tags derive from the binding schema base rather than the run-scoped physical schema, because the live service refuses an update that keeps a table's name but changes its lineage tag ("No element with lineage tag ... in DataSources"); a staged run therefore keeps the tags of the run it replaces. Entity-relationship tags use the original relation and endpoint pair so adding another polymorphic pair does not by itself change the tag of the original logical edge type.

There is an unavoidable limitation in rename stability. A UUID derived from an entity or property name cannot remain identical when that name changes. This implementation follows the specified name-based UUID formula rather than claiming rename-stability that it cannot deliver. Table and TOM relationship identities can also change when a formerly monomorphic relation becomes polymorphic and its specified physical name changes. True rename-stability needs an explicit immutable object identifier or a persisted lineage registry, neither of which is part of contract version 1. Adding such a registry is a recommended next design change.

Each `land` run has a `_landing-manifest.json` recording file content hashes. The uploader freezes file bytes before sending them. Reusing the run identifier with a different snapshot is rejected instead of silently leaving old remote files behind. This is an additional safety restriction beyond simple overwrite-upload. The framework archive itself is source-only, ordered by relative filename, and has fixed ZIP timestamps. Its twelve-character SHA-256 prefix versions the archive. This is a content-version check, not a digital signature or a replacement for storage access control.

Preparation persists `prepare-status.json` as `writing` before table writes and as `complete` only after all tables, the quality report and plan succeed. The marker contains an input fingerprint, schema ownership, the plan digest and a reusable summary. A completed staged snapshot is immutable: an unchanged repeat reuses it without writes, while changed input or settings require a new run identifier. A failed run can resume only with matching input and ownership. A `writing` marker is not assumed to be abandoned; callers must wait or choose another run identifier. Existing unowned schemas are never overwritten. Framework-generated plans require a matching complete marker to publish; standalone legacy plans without publication metadata remain supported without automatic retention.

Local report writes use exclusive sibling files followed by atomic replacement. Staged mode derives independent raw and binding schemas from their configured base, sanitized run identifier and a twelve-hex digest of the original base and run identifier. Names contain only lowercase letters, digits and underscores and fit within 120 characters. Case or punctuation normalization therefore cannot collapse distinct run identifiers onto one schema. The plan’s optional `publication` object records `mode`, `rawSchemaBase` and `bindingSchemaBase`, and validation checks the actual schema names against that ownership metadata.

Staged publishing verifies all binding counts before switching the ontology, preserves the existing required-table SQL refresh checks, and verifies the published definition and counts before recording publication. A per-ontology catalog under `Files/_ontology_ingest/_publications/` retains the newest `retain_runs` successful publications. The default of two keeps the current and previous snapshots available for rollback. Older tracked staged raw and binding schemas are deleted through the table storage adapter, never by deleting Fabric items. Schema names are checked against recorded ownership before cleanup, and retained references in other framework publication catalogs protect shared snapshots. A cleanup failure remains pending for a later successful publication instead of pretending the storage was deleted.

Retention deliberately covers tracked successful publications, not arbitrary schemas, failed or never-published runs, or manually created resources. Unpublished and in-flight schemas remain for investigation or explicit operator cleanup. Shared in-place base schemas and legacy schemas are never automatically deleted. Keep a single writer per run identifier and serialize publication/catalog updates within a lakehouse; this implementation does not supply a distributed lease or compare-and-swap catalog transaction. Switching an existing installation to staged mode requires a fresh run identifier. An explicit `in_place` mode remains available, but its per-table overwrites can expose mixed data during failure and do not provide immutable rollback snapshots.

Determinism is defined relative to the source files, metadata, run identifier and clock. The injectable `now` parameter makes plan, report and raw-audit tests byte-for-byte reproducible. Live ingestion timestamps naturally change on a new run. Delta physical filenames and transaction history are delegated to the Delta library and are not promised to be byte-identical across equivalent writes.

## Delta, transport and notebook decisions

The package requires only the standard library and pyarrow. `deltalake` is imported lazily. Local writing uses real Delta if the library is importable, otherwise it writes Parquet plus `_format.json`. That fallback is intentionally labelled `parquet-fallback`, is never called a managed Delta table, and is never used for OneLake output. A fallback write cannot overwrite an existing Delta table. The writer inspects the installed `write_deltalake` signature and chooses `schema_mode="overwrite"` or the older `overwrite_schema=True`. It does not pass `engine`, deletion-vector or column-mapping options. A notebook runtime with deltalake 0.18.2 and a newer local installation can therefore each use their supported signature, and the tests exercise both API shapes with fakes, so the suite needs no real Delta installation.

`http` provides injectable urllib I/O with bounded retry counts, backoff, `Retry-After`, request timeouts and operation deadlines. PATCH requests are not retried by default, and OneLake append and flush explicitly disable request-level retries. If append, flush or the final HEAD length check fails after create, the uploader deletes the partial file, ignores a delete 404, and restarts the entire file once from creation. A second failure is cleaned up and raised. HEAD must return a valid Content-Length equal to the intended byte length. Initial file creation deliberately omits If-None-Match, so a repeated archive upload overwrites the earlier copy, as OneLake allows. Other HTTP operations retain their existing bounded retry policy; ambiguous connection failures are not blindly replayed. Per-thread urllib openers and locked token-redaction bookkeeping support concurrent landing uploads.

Continuation and polling URLs must remain on the configured HTTPS origin. Automatic redirects are disabled rather than risking bearer-token forwarding to another host. HTTP exceptions include response text and a request identifier while redacting all tokens used by that client, including tokens from earlier retry attempts. Delta library exceptions are similarly redacted. Tokens are never written to state, plans, configuration or reports. Azure CLI tokens are cached using their JWT expiry with the requested five-minute margin. An opaque token without an expiry is not cached; inventing a lifetime was rejected. Notebook tokens are obtained lazily through the supplied audience key.

The notebook metadata is centralized and overridable. Its default follows the Jupyter kernel and language metadata that Fabric notebooks use, including every code cell's language group and the parameter-cell tag. The bootstrap cell is independent of the package being downloaded. It uses the storage token, verifies the archive content hash, and zipimports the package. It uses a relative `.ontology_ingest` cache rather than an absolute `/tmp` location, keeping generated files in a controlled working-directory location. No package extraction is needed. The run cell invokes shared orchestration and returns a JSON exit string. `build_framework_zip` refuses any file whose name is not an importable module name, such as the "fabric 2.py" conflict copies a sync client can leave beside rapidly rewritten files, rather than shipping it in the archive.

The notebook job helper polls on the configured API origin. A regional Location is mapped only when its HTTPS path is exactly the documented job-instance path for the requested workspace and notebook, with no credentials, query or fragment. The regional host is never contacted and an unrelated operation identifier is not confused with the job identifier. The existing generic LRO mapping by `x-ms-operation-id` or a validated operations path is preserved. After job completion, exitValue is read from the notebook-specific execute-instance route. Notebook run cells preserve structured error exits, and the CLI raises on those errors rather than treating an HTTP-completed job as application success.

SQL endpoint refresh accepts only Success, or NotRun accompanied by a last successful sync time, and requires every requested binding table to be present in that accepted set. Failure, Skipped, Completed and Succeeded table statuses are not silently accepted as successful synchronization. When binding tables are named, only they must sync, and any other table that fails is logged as a warning, because the lakehouse is shared and a table the ontology does not bind must not block a publish; without names, every listed table must sync.

The MCP client initializes protocol version `2025-06-18`, sends the initialized notification, retains any session identifier, and increments JSON-RPC request identifiers. It handles plain JSON and event-stream responses, ignoring unrelated notifications and matching the response identifier. The default transport stops reading a stream when the matching result arrives rather than waiting indefinitely for a persistent connection to close. Tools are discovered instead of hard-coding the observed tool list into the framework.

The graph helper follows the [documented GQL query API](https://learn.microsoft.com/fabric/graph/gql-query-api). An HTTP 200 response with application status `02000` and `result.nextPage` is still in progress. The helper repeats the same POST body and adds the opaque token as `continuationToken`, percent-encoding the token exactly once using RFC 3986 rules. Repeated in-progress tokens are allowed. The helper collects `result.columns` and `result.data` until there is no next page, rejects column-schema drift, and returns `columns`, `rows`, the final `status`, accumulated `warnings`, and a `truncated` flag. Configurable execution and page budgets bound polling; the defaults permit the documented twenty-minute server execution window. HTTP 429 honors bounded `Retry-After`, and an HTTP 408 `QueryTimeout` is raised without retrying it as a new query.

Application errors `42000` and `50000` raise even when the HTTP response is 200, with the status description and `_graphaneGqlStatus` diagnostics included in a token-redacted exception. The live service sends that diagnostic as a typed value, such as `{"gqlType": "STRING", "value": "42000"}`, and the helper reads it in that form as well as a bare string. Application status `00001` preserves the omitted-result status, and `02000` without a next page is a terminal empty result. Public `01000` statuses are returned as warnings. A truncation diagnostic `01M11` sets `truncated` and remains in the warning details; omitted rows are not presented as recoverable by further pagination.

## Configuration schema and command semantics

Configuration is a JSON object with the following supported shape. All filesystem paths are resolved relative to the configuration file, not relative to the shell's working directory. Unknown top-level keys are rejected, and there is no field for an access token, password or client secret.

```json
{
  "workspace_id": "11111111-1111-1111-1111-111111111111",
  "lakehouse_id": "22222222-2222-2222-2222-222222222222",
  "lakehouse_name": "ExampleLakehouse",
  "ontology_name": "ExampleOntology",
  "ontology_description": "A reusable example ontology.",
  "graph_model_name": "ExampleGraph",
  "landing_root": "../landing",
  "output_dir": "../output",
  "run_id": "example-20261106",
  "raw_schema": "raw",
  "binding_schema": "dbo",
  "publish_mode": "staged",
  "retain_runs": 2,
  "notebooks": {
    "prepare": "ExampleOntology prepare",
    "generate": "ExampleOntology generate",
    "graph": "ExampleOntology graph"
  },
  "pipelines": {
    "ingest": "ExampleOntology ingest",
    "copy": "ExampleOntology copy dataset"
  },
  "sql_endpoint": {
    "host": "example.datawarehouse.fabric.microsoft.com",
    "id": "33333333-3333-3333-3333-333333333333"
  },
  "notebook_kernel_metadata": null,
  "mcp_smoke": false
}
```

`workspace_id`, `ontology_name` and `landing_root` are required nonempty strings. A nonempty `lakehouse_id` or `lakehouse_name` is also required. Identifiers must parse as GUIDs. When the identifier is absent, live orchestration finds a lakehouse by display name and creates a schema-enabled one if necessary. When an identifier is supplied, the caller is responsible for selecting a schema-enabled lakehouse. `lakehouse_name` is optional when an identifier is supplied. Ontology, lakehouse and notebook names are limited to 512 characters and cannot contain control characters, path separators or namespace markers.

`ontology_description` is an optional string with an empty default and a strict 256-character item-metadata limit. Entity and property descriptions have their separate TMDL limits. `run_id` is an optional string; the command-line override wins, and an omitted or empty value generates a UTC timestamp identifier. A nonempty run identifier must match `[A-Za-z0-9][A-Za-z0-9_.-]{0,119}`. `output_dir` defaults to `output` beside the configuration file and must not be within `landing_root`. It holds local state and verification reports under a run-specific directory. State records workspace and ontology identity and refuses accidental reuse with another workspace, ontology or explicitly different lakehouse.

`raw_schema` and `binding_schema` default to `raw` and `dbo` and must be distinct lowercase identifiers matching `[a-z][a-z0-9_]*`. In the default `publish_mode: "staged"`, they are schema bases, not the final physical schema names; the exact run-scoped names are in the returned summary and ontology plan. Set `publish_mode: "in_place"` explicitly to use those base schemas directly. `retain_runs` is an integer of at least one, defaulting to two, and counts the current verified publication as one retained run. Both execution engines and generated notebooks receive these options.

If `notebooks` is provided, it must contain distinct `prepare` and `generate` display names and may also name the `graph` notebook. If absent or null, names are generated from the ontology name with those suffixes, and a missing `graph` name is generated the same way. `notebook_kernel_metadata` is null by default or an object replacing the default kernel block, while lakehouse dependency metadata is always attached separately.

If `pipelines` is provided, it must contain exactly the `ingest` and `copy` display names, distinct from each other and from the notebook names. If absent or null, they default to the ontology name followed by `ingest` and `copy dataset`.

`sql_endpoint` is null by default or an object containing exactly two nonempty strings, `host` and `id`. It is only an offline rendering hint. Live generation always reads the actual endpoint from the lakehouse response. Without this hint, dry runs render the explicitly marked `unresolved.invalid` endpoint and a zero GUID. Those placeholder parts are not evidence of a deployable live definition.

`mcp_smoke` defaults to false. Setting it to true performs initialization and tool discovery. It may instead be an object with a nonempty `name` and an optional object-valued `arguments`; that form discovers tools and calls the named tool. For the ontology's MCP server, a useful request is `{"name":"ask_ontology","arguments":{"request":"List the available entity types."}}`. Its tool requires a request string of 3 to 10,000 characters. The general client leaves tool-specific validation to the discovered server schema rather than imposing that one tool's schema on all tools.

`graph_model_name` is optional, with an empty default. When it is set, `graph-model` publishes a graph model of that name over a run's binding tables, `run` ends with that step, a dry run also writes the graph model definition under `dry-run/graph-model/`, and `graph` reads that graph model. It follows the same rules as the other item names and must differ from the ontology name.

The command format is `python -m ontology_ingest --config config.json <command>`. The parser also accepts `--config` after the subcommand. `land` publishes source files and the framework archive. `deploy-notebooks` publishes the prepare and generate notebook definitions, and the graph notebook when `graph_model_name` is set, and requires a previously landed framework archive. `prepare --engine fabric` runs the prepare notebook; `prepare --engine local` runs the same preparation code on this interpreter against OneLake. Local engine does not mean local storage. `generate` has the same engine distinction. `verify` reads the plan, counts both entity and junction tables, checks the ontology definition and optionally performs the MCP smoke test. `graph-model` publishes, reloads and verifies the graph model for a published run, and always runs on this interpreter. `deploy-pipeline` deploys the notebooks and then the copy and ingest pipelines, writing the landed archive's path and hash and the other fixed notebook settings into the ingest pipeline. `run-pipeline` starts the ingest pipeline through the job scheduler with `run_id` as its only parameter, waits for it, collects every activity run, following each child pipeline run, into `pipeline-run.json`, and fails unless the run completed. `run` performs landing, notebook deployment, preparation, generation, verification and, when `graph_model_name` is set, the graph model step, in that order; with `--engine pipeline` it performs landing, pipeline deployment, the pipeline run and verification instead. It stops at the first error. A pipeline run id must match `[a-z0-9][a-z0-9_]{0,59}`, and without `--run-id` the pipeline engine names the run after the current UTC time in lowercase.

`--dry-run` is an offline planning mode for every subcommand. It reads local landing data and uses fresh in-memory tables and report storage on each invocation, then writes its artifacts under `<output_dir>/<run_id>/dry-run/`. Repeating a dry run does not attempt to reuse vanished in-memory tables or overwrite a managed preparation marker. It renders the configured publication mode but does not publish, prune storage, acquire a token or instantiate authenticated clients. For persistent local data, use `prepare.run` with `LocalDeltaWriter`. Custom staged writers must also implement schema existence checks; publication/retention adapters additionally provide row counts and schema deletion.

Remote preparation artifacts live in `Files/_ontology_ingest/<run_id>/`. Raw and binding tables live in `Tables/<schema>/<table>`. Landing snapshots live in `Files/landing/<run_id>/`, and framework archives live in `Files/_framework/<hash>/ontology_ingest.zip`. File-store paths in summaries are relative to the chosen file-store root. The CLI's remote file store is the lakehouse `Files` root.

## The Fabric pipeline

`pipeline.py` builds two Data Factory pipeline definitions, and [FABRIC_KNOWLEDGE.md](../../docs/FABRIC_KNOWLEDGE.md) describes them for a reader who wants to run them. The ingest pipeline checks its `run_id` parameter, lists the dataset folders under `Files/landing/<run_id>/` with Get Metadata, filters out names that begin with an underscore, and for each folder, three at a time, calls the copy pipeline through the legacy Invoke pipeline activity, which runs pipelines of the same workspace without a stored connection. The copy pipeline lists the folder's `entities` and `relationships` subfolders with the `exists` field, so a missing subfolder yields an empty list through the null-safe `?.` operator instead of an error, keeps the CSV files and copies each one, six at a time, into a Delta table named by `naming.raw_table_name`, which the pipeline mirrors in its own expression. The ingest pipeline then runs the prepare, generate and graph notebooks in turn, with `raise_errors` set so that a notebook failure fails its activity. Data Factory does not allow a ForEach loop inside another, which is why the file loop lives in a second pipeline.

A pipeline run's raw schema is `raw_<run_id>`, computed by `naming.pipeline_raw_schema` and by a `concat` expression in the pipeline, because the expression language has no hash function; in-place publication uses the base schema instead. The prepare notebook receives that schema as `raw_tables_schema`, reads each copied table instead of the file it came from, takes the file's digest for the snapshot fingerprint all the same, and writes raw tables only for files the pipeline did not copy, such as JSON Lines files. It records `rawSchemaNaming: "pipeline"` in the publication metadata and refuses to continue unless the schema the pipeline wrote is exactly the one that rule predicts, so the ownership check and retention both recognise the unhashed name. `PublicationPlan.to_dict` omits the field for the default hashed naming, so the status files, fingerprints and catalogue records of command-line runs keep their earlier form. Copy activities use the documented `OverwriteSchema` table action; the undocumented `Overwrite` was accepted by the service but left a `<table>_backup_<guid>` table beside every table it replaced.

## Deliberate departures and additional safety policies

The working-directory notebook cache, raw-header sanitization and immutable run snapshots are deliberate safety choices, and so are these policies: missing values are normalized across all input formats, candidates are cast before priority selection, conflicts compare typed values, valid edges alone determine relationship naming, and decimal declarations bind as double. Staged publication and two-run retention are the default. Native TOM relationships omit lineage tags, while supported objects retain them. Range units carry one explicit exception for dimensional units, because rejecting every digit would break valid square-kilometre area values.

There is no claim of bytewise service round-trip identity. Structural verification is intentional. There is also no claim that the local Parquet fallback can be deployed as Delta. Without deltalake installed the optional real-Delta case is skipped, and an interpreter with deltalake runs it. No dependency installation or cloud request is needed for either suite.

## Architectural critique and next changes

The separation of a producer contract, preparation plan and TMDL renderer is useful because a domain producer can evolve without learning the cloud API. A single preparation implementation avoids divergent local and notebook transformations. Explicit Arrow schemas, deterministic names, fake transports and golden files make the important boundaries testable without a capacity or credentials. A source-only framework archive is a practical first distribution mechanism for notebooks.

Staged schemas and a verified-publication catalog now address the original live-overwrite weakness and retain the prior data snapshot for rollback. The remaining consistency gap is distributed coordination: catalog updates do not have a lease or compare-and-swap, and schemas must remain immutable outside this framework. I would next add a lease, table-version or content fingerprints for verification beyond row counts, and an explicit administrative workflow for orphan cleanup and rollback. Publication is a service definition switch rather than a cross-service transaction; a failed post-publish verification preserves prior snapshots but does not automatically roll the service back.

I would also add per-property winner provenance and provenance-aware groups of derived values. A column-wise merge can legitimately choose a display string from one source and a numeric derivative from another. A provenance record should explain that choice directly. Repeatedly inferring types from current rows can change a property type between runs; a governed schema policy should require approval or an explicit migration when that happens. A persistent property-name registry would prevent collision suffixes from shifting as new raw keys appear.

For larger models, I would make property selection explicit rather than promoting every property automatically. Otherwise a wide producer can consume the model's table-and-column budget without contributing useful ontology vocabulary. I would add a transformation plug-in boundary for unit conversion and domain validation, while keeping the default parser conservative. At the expected tens-of-thousands-of-rows scale, an in-memory implementation remains simpler to inspect than introducing Spark or a distributed execution dependency prematurely.

Finally, I would isolate preview service contracts behind versioned adapters, add opt-in live contract tests against a disposable workspace, and record the precise definition and query capabilities observed there. A real ontology parser or a service validation endpoint would provide stronger assurance than this renderer's intentionally narrow structural parser. Offline tests prove local behavior and request shapes, not tenant rollout, authorization, managed-table registration or service acceptance.

## Platform behaviours and limitations

Several behaviours of the services shape the implementation. Creating a graph model starts a refresh by itself, so a second refresh request reports `Deduped`, while updating a definition does not. Version 1.1.0 of the graph model's data source schema requires `referenceName`. GQL reserves `label`, so queries must escape it as a property name, and the GQL status diagnostic is a typed value. Every entity type published through the public API is ineligible in **Manage graph**, because Update Definition keeps only one of the eight `ONT_` connection annotations, which is why the framework builds a separate graph model ([FABRIC_KNOWLEDGE.md](../../docs/FABRIC_KNOWLEDGE.md)). In the pipeline, copy activities write every column as a string into Delta tables with reader version 1 and writer version 2, and Get Metadata reports `exists: false` for a dataset without a `relationships` folder, which the null-safe expression turns into an empty list. The undocumented table action `Overwrite` leaves a `<table>_backup_<guid>` table beside each table it replaces, and such a table can fail to sync on the SQL analytics endpoint, so the copy activities use `OverwriteSchema`, which replaces each table in place as a new Delta version.

The framework also has known limitations. Concurrent publishers are unsupported, because the publication catalogue has no lease or compare-and-swap. Decimals bind as double. The direct MCP client does not implement the MCP tasks extension, so only the Foundry path uses background mode.

Before production use, review the end-user identity, item publication state, dataset permissions and sharing of the Foundry connection for least privilege, following the [official authentication guidance](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/fabric-iq#authentication-and-security).

## Verification and maintenance

The pytest suite blocks socket connections and accidental Azure CLI authentication. Its temporary fixtures and cache live under `tests`, and the fixture directory is removed at session completion. Tests cover producer determinism, raw parsing, merge priorities, conflicts, quantities, quarantine, explicit schemas, plan round trips, complete TMDL golden parts, invalid models, notebook code, reproducible zipimport, fake HTTP retries and polling, the corrected notebook exit-value route, MCP JSON and SSE handling, OneLake chunking, CLI dry runs, publication ordering and failed-run markers, the graph command's model lookup, readiness report and error mapping, the graph model definition, refresh, duplicate-refresh handling and count verification, the Foundry module's settings validation, paginated ontology lookup, agent guard and exit status, and the producers' borehole decoding, de-duplication, well resolution and outline checks.

The real landing integration copies only the supplied geology input into a project-local test directory, prepares it end to end using the in-memory writer, validates self-links and all requested polymorphic relations, verifies derived units, generates and checks the definition, and confirms that the original file hashes did not change. It skips only when that external example is unavailable. A separate real local Delta test runs when deltalake is installed and otherwise skips; the Parquet fallback and both Delta API signatures are always tested. Run the entire suite with `python3 -m pytest` from the framework directory. No live test is part of the default suite.
